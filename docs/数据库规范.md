# 储备表 APP 后端数据基座开发需求文档

## 0. 项目目标

本项目开发一个本地局域网部署的数据处理后端，用于接收运营每月期多次上传的四张 Excel 表，完成数据清洗、班期锁定、指标计算、四张完善表生成、统计大表沉淀、单期看板查询、同月内两期对比查询和 Excel 下载。

后端优先独立跑通，前端后续只需要调用接口完成上传、查看、筛选、对比和下载。

---

## 1. 技术栈要求

### 1.1 后端技术栈

* Python 3.11+
* FastAPI
* PostgreSQL
* SQLAlchemy 2.x
* Alembic
* Pandas
* OpenPyXL
* Pydantic v2
* Uvicorn

### 1.2 本地部署目标

本系统最终部署在一台本地局域网服务器电脑上，其他用户通过局域网访问前端页面。数据库使用 PostgreSQL，本地保存 Excel 文件和导出文件。

### 1.3 本次开发重点

本阶段重点开发后端数据基座，不要求复杂前端。需要提供可测试 API 和基础 Swagger 文档。

## 2. 业务规则

### 2.1 月期规则

系统最大业务单位是“月期”，例如：

```text
2026-06
2026-07
```

不同月期之间互不影响。每个月期的数据独立统计、独立计算、独立对比。

---

### 2.2 上传规则

每个月期内允许多次上传，每次上传称为一次正式上传次数：

```text
第 1 次上传
第 2 次上传
第 3 次上传
...
```

每个月期预计上传 4-10 次左右。每次上传是一个 Excel 工作簿，工作簿内必须包含以下 4 个 sheet：

```text
储备明细表
每月班期表
每月目标表
已进线表
```

工作簿文件命名规则当前约定为：

```text
YYYY-X月班期-第n次-日期.xlsx
```

示例：

```text
2026-3月班期-第1次-0303.xlsx
```

后端需要解析出：

```text
period_code = 2026-03
upload_seq = 1
source_period_year = 2026
source_period_month = 3
source_record_mmdd = 0303
```

说明：

* 文件名中的日期字段当前只用于留档记录，不参与匹配、锁定和统计计算。
* `table_type` 不从文件名解析，而是从固定 sheet 名映射：
  `储备明细表 -> reserve_detail`
  `每月班期表 -> monthly_class`
  `每月目标表 -> monthly_target`
  `已进线表 -> inbound`
* 获客类型、项目可靠程度、课线项目等分类字段不能在后端写死枚举；只按上传文件中实际出现的类别参与后续统计和分析。

---

### 2.3 同次数覆盖规则

同一个月期、同一个上传次数、同一个工作簿如果重复上传，视为纠错覆盖。

例如已经上传：

```text
2026-3月班期-第2次-0310.xlsx
```

再次上传同名同次数文件时：

```text
2026-3月班期-第2次-0310.xlsx
```

系统应删除旧的 source/base/fact 结果，并采用最新版重新计算。

不同上传次数之间必须保留：

```text
2026-3月班期-第1次-0303.xlsx
2026-3月班期-第2次-0310.xlsx
2026-3月班期-第3次-0317.xlsx
```

这些都属于正式历史数据，不能互相覆盖。

---

### 2.4 班期锁定规则

每个月期的班期排班只由该月期第 1 次上传中的《每月班期表》决定。

规则：

```text
如果 period=2026-06 且 upload_seq=1：
    从 2026-6月班期-第1次-0626.xlsx 的《每月班期表》sheet 中读取班期时间
    写入 base.period_class_schedule
    作为 2026-06 全月固定排班

如果 period=2026-06 且 upload_seq>1：
    不再修改 base.period_class_schedule
    只校验后续上传的班期时间是否与锁定时间一致
```

注意：

* 每个月期的班期时间可能不同。
* 每条课线的班期时间也可能不同。
* 不允许在代码中写死班期时间。
* 不允许把“每月固定 4 个班次”写成固定字段。
* 班期应按数据行存储，而不是按 class_1、class_2、class_3、class_4 写成列。
* 班期时间字段锁定，但招生进度等字段可以读取当次上传的班期表。

---

### 2.5 四张表完善化规则

每次上传后，系统不仅要生成看板统计，还要生成四张“完善表”。

完善表 = 原始字段 + 系统计算字段 + 匹配字段 + 校验字段。

用户下载时下载完善表，而不是仅下载原始上传表。

需要生成：

```text
base.reserve_detail_completed
base.monthly_class_completed
base.monthly_target_completed
base.inbound_completed
```

---

### 2.6 月期统计大表规则

所有统计指标统一沉淀到一张事实大表：

```text
fact.monthly_snapshot_metrics
```

这张表是看板和两期对比的统一数据源。

每一行代表某个月期、某次上传、某个维度下的一组指标。

维度包括但不限于：

```text
all
course_line
class
area
province
city
bd
acquisition_type
```

---

### 2.7 两期对比规则

两期对比只发生在同一个月期内。

```text
当前 = upload_seq
上期 = upload_seq - 1
```

例如：

```text
2026-06 第 3 次上传
只和
2026-06 第 2 次上传
对比
```

不同月期之间不做对比。

如果 upload_seq = 1，则不展示两期对比。

如果某个 BD、城市、课线等只在本期出现，则上期为空，变化值按：

```text
本期值 - 0
```

如果某个 BD、城市、课线等只在上期出现，则本期为空，变化值按：

```text
0 - 上期值
```

## 3. 数据库设计

数据库只建一个：

```text
reserve_app
```

不按月份建库，不按上传次数建库，不动态创建 PostgreSQL 物理表。

使用以下 schema：

```text
meta      元数据
source    每次上传的四张清洗表
base      班期锁定表 + 四张完善表
fact      月期统计事实大表
```

---

## 4. 数据表设计

### 4.1 meta.periods

月期表。

```sql
create table meta.periods (
    period_id bigserial primary key,
    period_code text not null unique,
    period_month date not null,
    created_at timestamptz default now()
);
```

示例：

```text
period_code = 2026-06
period_month = 2026-06-01
```

---

### 4.2 meta.upload_batches

上传批次表。每个月期的每一次完整上传对应一条记录。

```sql
create table meta.upload_batches (
    batch_id bigserial primary key,
    period_id bigint not null references meta.periods(period_id),
    upload_seq int not null,
    source_period_year int,
    source_period_month int,
    source_record_mmdd text,
    uploaded_by text,
    uploaded_at timestamptz default now(),
    status text default 'uploaded',
    message text,
    unique(period_id, upload_seq)
);
```

---

### 4.3 meta.upload_table_instances

上传表实例表。每次上传的每张表对应一条记录。

```sql
create table meta.upload_table_instances (
    table_instance_id bigserial primary key,
    batch_id bigint not null references meta.upload_batches(batch_id),
    period_id bigint not null references meta.periods(period_id),
    upload_seq int not null,
    table_type text not null,
    sheet_name text not null,
    original_filename text,
    file_path text,
    file_sha256 text,
    row_count int,
    created_at timestamptz default now(),
    unique(period_id, upload_seq, table_type)
);
```

table_type 只能取：

```text
reserve_detail
monthly_class
monthly_target
inbound
```

sheet_name 只能取：

```text
储备明细表
每月班期表
每月目标表

```

## 9. 核心计算逻辑

### 9.1 获客天数

获客天数包含开始日期和结束日期当天。

```python
customer_days = (end_date - start_date).days + 1
```

如果开始日期或结束日期为空，则 validation_status 标记为 error。

---

### 9.2 下周获客天数

如果下周开始日期和下周结束日期都存在：

```python
next_week_customer_days = (next_week_end_date - next_week_start_date).days + 1
```

否则为 0。

---

### 9.3 每日拆分逻辑

以保底储备量为例：

如果存在：

```text
next_week_start_date
next_week_end_date
next_week_base_reserve_qty
```

则：

```python
base_reserve_daily_next_week = next_week_base_reserve_qty / next_week_customer_days
base_reserve_daily_other = (base_reserve_qty - next_week_base_reserve_qty) / (customer_days - next_week_customer_days)
```

如果不存在下周字段：

```python
base_reserve_daily_next_week = 0
base_reserve_daily_other = base_reserve_qty / customer_days
```

保底预测业绩、冲高储备量、冲高预测业绩同理。

---

### 9.4 班期归因逻辑

对每条储备明细，根据：

```text
course_line
metric_date
```

匹配：

```text
base.period_class_schedule.course_line
base.period_class_schedule.inbound_start_date <= metric_date <= inbound_end_date
```

把每日指标加总到班期，生成：

```text
base.monthly_class_completed
```

注意：

* 班期时间只能来自 base.period_class_schedule。
* 后续上传中的班期时间不得覆盖锁定时间。
* 后续上传班期表中的招生进度可以使用。

---

### 9.5 招生进度处理

如果 enrollment_status = 已结束：

```text
final_stretch_reserve_qty = null
final_stretch_forecast_revenue = null
```

如果 enrollment_status = 招生中：

```text
final_xxx = calc_xxx
```

即系统计算值覆盖人工预填值。

其他状态默认：

```text
final_xxx = calc_xxx
```

具体状态值需要支持配置，避免中文状态写死在核心逻辑中。

### 9.6 总储备量与总预测业绩

```text
保底总储备量 = 已进线量 + 保底储备量
冲高总储备量 = 已进线量 + 冲高储备量

保底总预测业绩 = 已达成预测业绩 + 保底预测业绩
冲高总预测业绩 = 已达成预测业绩 + 冲高预测业绩
```

```text
保底达标率 = 保底总预测业绩 / 预测业绩目标
冲高达标率 = 冲高总预测业绩 / 预测业绩目标
```

如果目标为空或为 0：

```text
achievement_rate = null
validation_status = warning
```

## 10. 上传处理流程

实现一个完整服务：

```text
UploadService
```

流程：

```text
1. 接收一个 Excel 工作簿
2. 校验工作簿文件名格式
3. 解析 period_code、upload_seq
4. 校验工作簿必须包含固定四个 sheet
5. upsert meta.periods
6. upsert meta.upload_batches
7. 对四个 sheet 分别 upsert meta.upload_table_instances
8. 删除该 period_id + upload_seq 的旧 source 数据
9. 删除该 period_id + upload_seq 的旧 base completed 数据
10. 删除该 period_id + upload_seq 的旧 fact 数据
11. 解析工作簿四个 sheet 到 source 四张表
12. 如果 upload_seq = 1 且该月期没有锁定班期：
        生成 base.period_class_schedule
13. 如果 upload_seq > 1：
        校验本次 monthly_class_rows 的班期时间是否与 period_class_schedule 一致
14. 生成四张 completed 表
15. 生成 fact.monthly_snapshot_metrics
16. 返回处理结果
```

## 11. 覆盖删除逻辑

同一个 period_id + upload_seq 重传时，需要删除：

```sql
delete from fact.monthly_snapshot_metrics
where period_id = :period_id and upload_seq = :upload_seq;

delete from base.reserve_detail_completed
where period_id = :period_id and upload_seq = :upload_seq;

delete from base.monthly_class_completed
where period_id = :period_id and upload_seq = :upload_seq;

delete from base.monthly_target_completed
where period_id = :period_id and upload_seq = :upload_seq;

delete from base.inbound_completed
where period_id = :period_id and upload_seq = :upload_seq;

delete from source.reserve_detail_rows
where period_id = :period_id and upload_seq = :upload_seq;

delete from source.monthly_class_rows
where period_id = :period_id and upload_seq = :upload_seq;

delete from source.monthly_target_rows
where period_id = :period_id and upload_seq = :upload_seq;

delete from source.inbound_rows
where period_id = :period_id and upload_seq = :upload_seq;
```

注意：

```text
base.period_class_schedule 不随 upload_seq > 1 删除。
```

只有当 upload_seq=1 被覆盖时，才允许重建该月期的班期锁定表。

## 13. 两期对比 SQL 逻辑

两期对比使用 full outer join，兼容某个维度只在本期或上期出现。

```sql
select
    coalesce(cur.dimension_level, prev.dimension_level) as dimension_level,
    coalesce(cur.dimension_key, prev.dimension_key) as dimension_key,
    coalesce(cur.dimension_name, prev.dimension_name) as dimension_name,

    cur.base_total_reserve_qty as current_base_total_reserve_qty,
    prev.base_total_reserve_qty as previous_base_total_reserve_qty,
    coalesce(cur.base_total_reserve_qty, 0) - coalesce(prev.base_total_reserve_qty, 0)
        as diff_base_total_reserve_qty,

    cur.base_total_revenue as current_base_total_revenue,
    prev.base_total_revenue as previous_base_total_revenue,
    coalesce(cur.base_total_revenue, 0) - coalesce(prev.base_total_revenue, 0)
        as diff_base_total_revenue,

    cur.stretch_total_reserve_qty as current_stretch_total_reserve_qty,
    prev.stretch_total_reserve_qty as previous_stretch_total_reserve_qty,
    coalesce(cur.stretch_total_reserve_qty, 0) - coalesce(prev.stretch_total_reserve_qty, 0)
        as diff_stretch_total_reserve_qty,

    cur.stretch_total_revenue as current_stretch_total_revenue,
    prev.stretch_total_revenue as previous_stretch_total_revenue,
    coalesce(cur.stretch_total_revenue, 0) - coalesce(prev.stretch_total_revenue, 0)
        as diff_stretch_total_revenue

from fact.monthly_snapshot_metrics cur
full outer join fact.monthly_snapshot_metrics prev
  on cur.period_id = prev.period_id
 and cur.dimension_level = prev.dimension_level
 and cur.dimension_key = prev.dimension_key
 and prev.upload_seq = cur.upload_seq - 1
where coalesce(cur.period_id, prev.period_id) = :period_id
  and coalesce(cur.upload_seq, prev.upload_seq + 1) = :upload_seq
  and coalesce(cur.dimension_level, prev.dimension_level) = :dimension_level;
```

## 16. 错误处理

### 16.1 文件名错误

如果文件名不符合：

```text
YYYY-X月班期-第n次-日期.xlsx
```

返回 400。

---

### 16.2 工作簿 sheet 不完整

如果一次上传的工作簿缺少任意一个约定 sheet，返回 400。

---

### 16.3 sheet 名错误

如果工作簿存在未约定 sheet，或 sheet 名拼写错误，返回 400。

### 16.4 后续上传修改了班期时间

如果 upload_seq > 1 且班期时间与 base.period_class_schedule 不一致，返回 400 或 warning。

默认先返回 400，避免后续数据污染。

---

### 16.5 计算字段缺失

如果核心日期或指标缺失：

```text
validation_status = error
validation_message 写明原因
```

该行不参与对应指标计算。

## 19. 验收标准

项目完成后，应满足：

1. 后端可以独立启动。
2. 可以上传一个月期某一次的完整工作簿，且工作簿内包含固定四个 sheet。

8. 每次上传后生成 fact.monthly_snapshot_metrics。

11. 可以下载四张完善表组成的 Excel。
12. 所有核心计算异常行需要保留 validation_status 和 validation_message。
13. 所有接口可在 Swagger 中测试。

## 20. 重要实现原则

1. 不要动态创建 PostgreSQL 物理表。
2. 不要按月份建数据库。
3. 不要按上传次数建数据库。
4. 不要把 4 个班次写成 4 个固定字段。
5. 不要让前端承担核心计算。
6. 不要让前端承担两期对比计算。
7. source 层保存上传清洗内容。
8. base 层保存班期锁定和四张完善表。
9. fact 层保存统计大表。
10. 所有下载和看板都应基于 base/fact，而不是直接基于原始 Excel。
